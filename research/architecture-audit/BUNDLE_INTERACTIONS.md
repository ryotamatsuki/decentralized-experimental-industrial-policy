# Bundle Interactions

Date: 2026-08-28

The purpose of this file is to test non-additivity. A bundle survives only if combining functions changes private behavior or project composition in a way not generated by either component alone.

## Deep non-additivity tests

### B6 — Scalability-by-Design Architecture

Minimal architecture:

`multi-site implementation requirement + public implementation finance + downstream replication support`

- **Requirement only:** raises fixed/adaptation cost and can deter suppliers, but screens out projects that cannot travel across local users.
- **Finance only:** relaxes implementation cost but may finance highly bespoke one-off projects.
- **Diffusion support only:** subsidizes later adoption but does not determine which initial projects become validated reference solutions.
- **Bundle:** the finance can compensate suppliers for costly multi-site validation while the multi-site requirement changes the composition of financed projects; anticipated replication can raise the value of designing a reusable solution. The architecture may therefore change both **entry** and **product/project design**.

Potential research question:

> When can a public programme improve the composition of technology projects by tying implementation finance to multi-site scalability requirements and then supporting replication, rather than subsidizing pilots or later adoption in isolation?

Immediate kill condition: if the complete logic is equivalent to a standard screening contract with an exogenous market-size benefit, or if downstream support adds only a separable demand shift.

### B13 — Reference-Market-to-Private-Market Transition

Minimal architecture:

`publicly financed implementation at private/local users + reference/packaging stage + private follow-on adoption support`

Potential novelty is not certification itself. It would require the identity of the buyer to change endogenously: the public actor finances/organizes an initial private implementation, while subsequent adopters transact voluntarily with the supplier. The architecture would be a bridge from an incomplete market to a private one.

Immediate kill condition: if this is standard PPI certification, lead-market demand pull or infant-industry support with a relabeled buyer.

### B9/B10 — Implementation-to-Replicable-Offering

Implementation experience plus packaging plus downstream demand may convert a bespoke deployment into a reusable product. This is institutionally plausible, but the formal core is close to product design, learning-by-doing and demand pull.

Immediate kill condition: if “packaging” is simply an exogenous reduction in adaptation cost.

## Architecture-level inference

The audit does **not** conclude that more instruments are better. The strongest candidate works only because the components may have opposing selection effects: a scalability requirement can reduce entry, implementation finance can expand entry, and replication support can change the value of reusable design. That tension is the reason B6 deserves a dedicated novelty audit rather than immediate modelling.
